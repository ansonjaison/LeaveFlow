1 Database Schema — Entity Relationship

The database has two core tables: employees and leave_requests. Each employee can submit multiple leave requests. The employee_id in leave_requests acts as a foreign key referencing the employees table, forming a one-to-many relationship. Supabase Auth UIDs are stored as the auth_uid field to link each employee record to their authenticated identity.

One-to-Many: employee → leave_requests auth_uid links Supabase Auth ↔ DB record UUID primary keys throughout

2 Employees Table — Sample Data

The employees table stores each user's profile information including their name, email, department, role (ADMIN or EMPLOYEE), leave balance, and their Supabase auth_uid. The is_active flag lets admins deactivate accounts without deleting them.

Columns: id, name, email, department, role, leave_balance, auth_uid, is_active Role-based access: ADMIN vs EMPLOYEE leave_balance tracks remaining days

3 Leave Requests Table — Sample Data

The leave_requests table records every leave application submitted by employees. It tracks the leave type (SICK, CASUAL, ANNUAL), start/end dates, working days consumed, status (PENDING, APPROVED, REJECTED), and optional rejection reason provided by the admin.

Statuses: PENDING · APPROVED · REJECTED Types: SICK · CASUAL · ANNUAL working_days skips weekends automatically rejection_reason stored for transparency

4 Supabase Auth — Registered Users

Supabase Auth manages user registration, password hashing, and JWT token issuance. Every registered user gets a unique auth.users entry in Supabase. On login, Supabase returns a signed JWT which the frontend stores and sends as a Bearer token on every API request. The Spring Boot JwtFilter intercepts each request, validates the token via Supabase's public key, and injects the authenticated user identity into the Spring Security context.

JWT issued and validated by Supabase JwtFilter → Spring Security context auth_uid matches employees.auth_uid

🔐 Authentication & Request Flow

1
Login Employee enters email + password → Frontend calls Supabase Auth API → Supabase returns a signed JWT access token.
2
Token Storage JWT is stored in localStorage and attached as Authorization: Bearer <token> on every subsequent API call.
3
JwtFilter (Spring Boot) Intercepts every request, extracts the JWT, validates it against Supabase's JWKS endpoint, and sets the security context with the user's auth_uid.
4
Employee Lookup Using auth_uid from the token, the backend fetches the matching employee record from the employees table to determine their role and permissions.
5
Role-Based Access ADMIN endpoints (manage employees, approve/reject leaves) are protected by role checks. EMPLOYEE endpoints only allow access to their own data.

  "leaveBalance":      18,
  "active":            true,
  "generatedPassword": "Xk9#mP2z"

📋 Leave Request Endpoints  ·  /api/leaves
POST /api/leaves Submit a new leave request Employee (self) ▶
201 Created 400 Validation / Business error 403 Forbidden

📥 Request Body (JSON)

{
  "employeeId": 1,
  "leaveType":  "SICK",
    // SICK | CASUAL | ANNUAL
  "startDate":  "2025-07-10",
  "endDate":    "2025-07-12",
  "reason":     "Doctor appointment"
  // reason: max 500 characters
}

📤 Response Body (JSON)

{
  "id":              10,
  "employeeId":      1,
  "employeeName":    "Alice Johnson",
  "leaveType":       "SICK",
  "startDate":       "2025-07-10",
  "endDate":         "2025-07-12",
  "days":            3,
  "reason":          "Doctor appointment",
  "status":          "PENDING",
  "rejectionReason": null,
  "createdAt":       "2025-07-08T09:30:00"
}
Business validations enforced by LeaveService: sufficient leave balance, no overlapping approved requests, start date must not be in the past, end date ≥ start date. Employees cannot submit requests for other employees.

}

{

  "status":          "REJECTED",
  "rejectionReason": "Insufficient coverage...",
  ...
}
The rejectionReason is stored and shown to the employee on their dashboard. Leave balance is not deducted.
